---
title: "Tool Builder"
description: "Build your own toolkit from an existing HTTP API, classify each tool, and release it to a company"
---

The Tool Builder turns an existing HTTP API into a toolkit your agents can equip. You describe the API, the builder drafts one tool per endpoint, runs each one against a real connection, and — once every tool is classified and proven — the toolkit is released to a company.

Two decisions on every tool are **yours, not the builder's**: its human-approval requirement and its access level. Nothing reaches a customer until both are set.

---

## The three stages

<Steps>
  <Step title="Author">
    Draft a tool per endpoint: name, description, parameters, and the request it sends. Tool names are prefixed with the toolkit key (`hssoft_list_customers`) because a bare `list_customers` would collide with another toolkit or with a native Artaios tool.
  </Step>
  <Step title="Prove">
    Bind a connection and run each tool for real. The run is the evidence that the tool works — a successful run is frozen with the release.
  </Step>
  <Step title="Release">
    Freeze the toolkit as a version and point a company at it. Released tools appear in that company's own tool registry and can then be equipped in YAML like any built-in tool.
  </Step>
</Steps>

<Warning>
Running a tool calls the real API through the connection you chose. A `POST` or `DELETE` changes real data on that system. Know which connection is bound before you fire a write tool.
</Warning>

## Classifying a tool

Each tool carries two classification fields. Both are deliberately **empty by default** — there is no fallback value.

### `access`

<ParamField path="access" type="string" required>
  What the endpoint does to state.

  - `read` — `GET` / `HEAD` endpoints that only fetch data.
  - `write` — `POST` / `PUT` / `PATCH` / `DELETE` endpoints that create, update or delete state.
</ParamField>

### `hitl_requirement`

<ParamField path="hitl_requirement" type="string" required>
  Whether the tool pauses for human approval before it runs. This is the tool-source layer of the [Human-in-the-Loop](/documentation/agent_config/human-in-the-loop) precedence ladder — the strongest layer.

  - `never` — safe, read-only lookups and other low-risk operations. No gate.
  - `default_on` — consequential but reversible actions, for example sending a message to a default inbox. Pauses by default, but an agent author **can** opt out per instance with `disable_human_approval: true`.
  - `mandatory` — destructive, irreversible or financial operations: deleting records, deactivating accounts, permanent disables, payments. The pause **cannot** be overridden by any agent configuration.
</ParamField>

<Tip>
Use the strictest value that fits the endpoint. If you are unsure whether an operation is reversible in the customer's business, prefer `default_on` or `mandatory` over `never`.
</Tip>

<Note>
Why no defaults: whether an operation is reversible is a judgement about the customer's business that cannot be derived from an API spec. A silent `never` default is exactly how an unreviewed write tool would reach a customer, so the field stays empty until a human decides.
</Note>

### What the builder cannot decide

The drafting agent sets `access` and `hitl_requirement` as a proposal and must report its choice and reasoning for each tool. It has **no** ability to set a tool's interaction archetype or trace mode, and it cannot bind a connection outside the explicit connect step. A human reviews the classification before release.

## Release eligibility

A tool is not releasable until **all** of these hold:

| Requirement | Why it blocks |
|---|---|
| `hitl_requirement` is set | Unclassified approval behaviour |
| `access` is set | Unclassified read/write behaviour |
| The tool is declarative | Code-based tools are never production-eligible |
| Its spec validates | Malformed request definition |
| Its **most recent** run on the current shape succeeded | No proof it works |

<Warning>
An older success does **not** outvote a newer failure against the same request shape. If you change a tool and the new run fails, the toolkit stops being releasable even though it was releasable before — re-run it.
</Warning>

The release freezes one successful run per tool as evidence. That evidence is pruned when it stops meaning anything: superseded by a newer release, or left behind by a revoke.

<Note>
A release ships tool definitions and the authentication **schema** — never a credential. The customer's admin connects their own account afterwards in **Settings**.
</Note>

## Upgrading a released toolkit

When you release a new version over an existing one, two classification changes are flagged as **breaking**, because they silently remove a guard rail the customer already approved:

- **Weakening `hitl_requirement`** — `mandatory` → `default_on` → `never`. Nothing errors; an approval gate simply disappears. Reported as *"hitl_requirement weakened from 'mandatory' to 'default_on', removing an approval gate."*
- **Widening `access`** — `read` → `write`. A tool the customer accepted as read-only can now change their data.

Strengthening either direction is safe and is not flagged.

## Parameter visibility on approval forms

When a gated tool pauses, the reviewer sees a form built from the tool's parameters. Each parameter carries a visibility setting that controls how it appears:

| Visibility | On the approval form |
|---|---|
| `show` (default) | Rendered above the fold |
| `advanced` | Rendered inside the collapsed **Advanced** section; value flows through unchanged if untouched |
| `hidden` | Not rendered at all; the proposed value flows through unchanged |

Use `advanced` for plumbing a reviewer rarely touches (importance flags, content-type toggles with a sane default). Use `hidden` for implementation detail a human should never see — internal IDs, framework-only flags.

## Using a released toolkit

A released tool is registered in the owning company's namespace and is equipped like any other tool:

```yaml
persistent_state: true          # ← required if any equipped tool pauses for approval

agents:
  - name: "crm_agent"
    agent_type: "react_agent"
    tools:
      - "hssoft_list_customers"            # read, never — no gate
      - name: "hssoft_delete_customer"     # write, mandatory — always pauses
        tool_type: "hssoft_delete_customer"
```

<Note>
A tool released to a company is invisible outside it. Configuration validation is scoped to the owning company, so a config referencing another company's tool will not resolve.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Toolkit will not release">
    Check each tool against the [eligibility table](#release-eligibility). The most common causes are an unset `hitl_requirement` or `access`, and a tool whose last run failed after an edit.
  </Accordion>

  <Accordion title="Test run refuses to fire">
    No connection is bound to the toolkit. Bind one through the connect step — there is no alternative path, and the tool enforces that boundary with no exemption.
  </Accordion>

  <Accordion title="A released tool always pauses and I cannot disable it">
    It was classified `mandatory`. That is unoverridable by design — `disable_human_approval` is ignored against it. If the gate is genuinely wrong for the endpoint, the classification needs changing and the toolkit re-releasing, which is flagged as a breaking change.
  </Accordion>

  <Accordion title="Tool name rejected as a collision">
    Names must be unique across your company's toolkits and must not match a native Artaios tool. Prefix every name with the toolkit key.
  </Accordion>
</AccordionGroup>
